# First-server QR onboarding

A fresh Fleet installation shows the existing Fleet wing mark and one connection action: **Scan QR code**. It includes a copyable message for Hermes in a private Telegram conversation while the owner is at the host computer. The phone does not discover a host or create a network path. General users need a compatible, already-installed maintained Fleet host release and an HTTPS origin that the phone can reach and whose certificate iOS trusts. The app makes no host-discovery or automatic-install promise.

Before any invitation is issued, the host must verify that the actual incoming event is a private Telegram message from the verified owner authorized to manage this Hermes server. An allowlist or home channel alone is insufficient authority. The maintained Hermes Fleet host release's documented readiness report checks host capability for the exact source, runtime source, and Hermes home selection. It does not prove authority for the live Telegram event, forwarding, phone reachability or trust, or local QR display; those remain separate gates. Use the report to confirm that a compatible owner-bound issuer is installed and ready for the selected home and runtime. The host must verify that its configured HTTPS origin matches the invitation origin, is reachable from the phone, and presents a certificate trusted by iOS. Multi-label DNS HTTPS on a private network or tailnet can be used when the phone is a member of that network and trusts the certificate; public internet access and Funnel are not required. The computer must provide a private local QR display.

If readiness reports that the issuer is missing, the host reports the missing capability and asks the owner to provide or explicitly approve a trusted maintained Fleet host release and install path. Do not substitute a stock Hermes update, copy a single file, guess a download URL or command, or improvise an issuer. Installer activation requires explicit owner authority. No install, activation, or automatic escalation is implied by the copied prompt. Live invitation issuance also requires explicit owner authority; a ready report alone is not authorization to mint.

Only after host-tool readiness, the actual owner-bound request, origin reachability/trust, local display, and explicit authority to issue are verified may the host run the invitation command documented by that ready host tool for its detected Hermes home/runtime. Do not blindly run a legacy command on all installations. Capture the genuine issued output privately. Render the exact link locally, passing its bearer secret to the QR tool through standard input rather than command arguments. Keep any image private and remove it after use or expiry. Never transmit the bearer link or secret through Telegram, a group, command arguments, shell history, or logs. A synthetic QR round trip does not prove live Telegram authorization, the installed host capability, or a physical-phone scan.

The supported invitation format is the existing HTTPS `/pair` link with version, invitation ID and secret in its fragment. An invitation is scoped to its origin, short-lived and single-use. Scanning fetches a non-consuming preview. Fleet presents the host and its broad `fleet:operator` access, then requires **Connect this phone**. Back before confirmation leaves the invitation usable. Expired, used, cancelled, rate-limited, unreachable and untrusted responses show recovery instructions without exposing the link.

Redemption requires the same system-trusted public key as preview and refuses redirects. Ongoing authentication uses the existing `hfd1` device credential and DeviceLogin flow. The credential and confirmed TLS pin are securely saved before the fully configured gateway record is committed. Failed local saves trigger pinned remote revocation and local cleanup; unconfirmed cleanup is disclosed and retryable when the grant is still available. If a response is lost or the process terminates after redemption but before secure saving, the invitation may be consumed and the owner must check/revoke the orphaned device before issuing another invitation. The legacy server protocol does not offer client-generated-secret idempotency for this flow.

A saved gateway keeps its stable ID, credentials, pin and existing data; a configured user enters Fleet. Existing owner sign-in and manual authentication strategies remain in Advanced/additional-server setup, including the old JSON scanner decoder. First-server setup does not expose them. Production and Dev namespaces remain separate. Conversation deep links are unchanged.

Camera denial offers the app Settings action and Cancel. Simulator scan/denial fixtures are compiled only for DEBUG simulators. Fixture UI and temporary TLS gateway tests prove only the app's fixture flow; report them separately from actual host-tool readiness, live owner authorization, local QR display, phone network membership and certificate trust, physical-phone camera scanning, delivery, and enrollment acceptance.
