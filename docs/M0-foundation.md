## 1. Scope (M0 only)

Create the native Xcode project + git repo/workspace and establish the modular
SPM boundaries that preserve the fleet architecture. Explicitly NOT in M0:
live Hermes connection, `/api/ws`, JSON-RPC implementation, auth flow, Hermes
runtime/env/network changes, privileged controls, generated visual assets, and
all later milestone work.

## 2. Decisions (ADR-style)

### D1 — Modular monolith via local SPM packages + one app target
Each module is its own local Swift package under `Packages/`; the app target
(`HermesFleetApp`) is the only consumer of all of them. This enforces the
dependency graph at compile time (a module can only `import` what it declares).

### D2 — SwiftUI never depends on JSON-RPC/WebSocket plumbing
`FleetUI` declares dependencies on `FleetCore`, `FleetSecurity`,
`FleetPersistence` — **not** `FleetNetworking`. The transport seam
(`HermesTransport` protocol + `TransportState`) lives in `FleetCore`, so the UI
can depend on the abstraction without importing the transport module. Only the
composition root (`HermesFleetApp`) may depend on `FleetNetworking`.

### D3 — Deployment target and language mode
iOS 17.0+, Swift 6 language mode (SWIFT_VERSION 6.0), SwiftUI + Observation,
matching the project convention (IntervalTimer: iOS 17 / Swift 6) and the
prior planning architecture (t_982b20cc).

### D4 — project.yml is the single source of truth
Xcode project is generated by xcodegen; the generated `.xcodeproj` is committed
for reviewer convenience but any change goes through `project.yml` +
`xcodegen generate`. `DEVELOPMENT_TEAM: (team ID — see project.yml)` (verified from the Xcode
account store: "Anthony Simons (Personal Team)", free team) is persisted in
project.yml so regeneration never drops it.

### D5 — Package platforms include macOS for host-side testing
Packages declare `.iOS(.v17), .macOS(.v14)` so the pure `FleetCore` package can
run `swift test` on the host for fast feedback; the authoritative test path is
the iOS simulator test host (`xcodebuild test`).

## 3. Dependency direction (enforced)

```
FleetCore (no deps)
   ▲
   ├─ FleetNetworking ──> FleetCore
   ├─ FleetSecurity  ──> FleetCore
   ├─ FleetPersistence ──> FleetCore
   ├─ FleetUI ──> FleetCore, FleetSecurity, FleetPersistence
HermesFleetApp ──> all (composition root; only importer of FleetNetworking)
```

No cycles. A `import FleetNetworking` inside FleetUI fails to compile because
FleetUI does not declare it — this is the structural proof of the M0 guard.

## 4. What each module contains in M0

- **FleetCore** — pure value types (`GatewayID`, `ProfileSlug`,
  `AuthorizationClass`, `FleetGateway`) and the `HermesTransport` seam
  (protocol + `TransportState`). Own package tests (`FleetCoreTests`).
- **FleetNetworking / FleetSecurity / FleetPersistence** — boundary-only
  skeletons: a documented placeholder type that references a FleetCore type to
  prove the dependency compiles. No implementation (gated **at M0**).
- **FleetUI** — `FleetDashboardModel` (@MainActor @Observable), `FleetRootView`
  (NavigationStack shell), `FleetDashboardView` (empty state per the product
  spec's fleet-first model, with accessibility identifiers).
- **HermesFleetApp** — `@main` composition root that owns the model and
  injects it into `FleetRootView`.

## 5. Test strategy (M0)

- `FleetCoreTests` (package, host-run via `swift test`): identity equality/hash,
  codable round-trip, authorization lattice surface, transport-state equality.
- `HermesFleetAppTests` (hosted on simulator via `xcodebuild test`):
  - `FleetCoreLogicTests` — value-type logic on the iOS platform.
  - `ModuleBoundaryTests` — proves every module seam compiles/links and each
    exercises its declared dependency.
  - `AppCompositionTests` — app starts with an empty, inert fleet model.
- Coverage collection is enabled (`gatherCoverageData`) for the QA lane.
